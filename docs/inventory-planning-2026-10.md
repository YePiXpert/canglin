# 库存盘点、补货建议与采购跟进：详细实施方案

日期：2026-10-23。状态：已在 `1.0.0-beta.1` 实现；实际接口与验收见 [Beta 交付记录](release-1.0.0-beta.1.md)。本轮先交付库存盘点、低库存预警与补货草稿、采购跟进台三项；历史采购价对比和常用采购模板作为后续扩展。

设计依据为当前代码、`rebuild-requirements.md` 和上一轮付款与开票工作台。沿用单管理员、Vue / NestJS / Prisma / SQLite、整数定点数量与现有业务单据。上一轮工作区改动作为实施基础，不覆盖或丢弃。

## 1. 本轮交付与入口

目标流程：核对实物 → 确认库存差异 → 查看补货缺口 → 保存并确认补货草稿 → 采购 → 跟进到货与发票 → 明确入库。

| 入口 | 页面与操作 |
| --- | --- |
| 库存与领用 → 盘点 | 盘点列表、创建盘点、手机录入实盘数、差异核对、提交、撤销和历史详情 |
| 库存与领用 → 补货 | 安全库存设置、缺口解释、补货建议、草稿保存、转申请、查看已有补货进度 |
| 工作台 → 采购跟进 | 今日需跟进、逾期、未设计划、已完成、已忽略；跟进记录与原业务操作入口 |
| 工作台概览 | 待完成盘点、需补货物品、今日跟进数量；点击进入对应筛选 |
| 采购与申请详情 | 展示补货用途、预计到货日、下次跟进日和跟进记录；继续使用已有采购、到货、入库、付款与发票操作 |

建议路由：`/stock/counts`、`/stock/counts/:id`、`/stock/replenishment`、`/stock/replenishment/drafts/:id`、`/workbench/followups`。主导航仍使用现有业务入口，手机页签横向滚动。列表支持搜索、状态筛选、URL 保留条件和服务端分页。

提醒通过站内工作台和跟进列表呈现。未设置业务期限的记录显示“未设计划”；只有明确日期才判断是否逾期。

## 2. 库存盘点单

### 2.1 用户流程

1. 从库存勾选物品，或新建盘点后搜索添加物品；允许加入库存为零但需要核实的物品。单张最多 200 种物品，每种物品只有一行。
2. 保存标题、盘点说明和明细；系统记录每行的品名、规格、单位、账面库存、库存版本和基准时间。
3. 手机按行填写实盘数，填写一行后可保存、退出并继续。空白表示未盘，`0` 表示实物为零，两者严格区分。
4. 差异页展示账面数、实盘数、差额、差异原因；可筛选未盘、盘盈、盘亏和一致。差异行必须填写原因。
5. 确认页列出将产生的调整；提交后产生一张包含所有差异行的库存调整单，盘点记录和调整流水互相链接。
6. 无差异的盘点也可完成，保留核对记录，不创建零数量的调整流水。

提供盘点空表打印及结果 CSV 导出。手机采用逐项卡片和固定保存区域；退出未保存页面时提示保留或放弃，保存失败保留当前输入。

### 2.2 账目与并发规则

- 盘点范围是 `StockBalance.location = STOCK`。到货待处理的 `RECEIVING` 单独显示，不混进账面库存。
- 数量允许零，不能为负，最多六位小数；API 继续使用十进制字符串，数据库继续用 BigInt 定点数。
- 新增物品级 `stockVersion`：每次实际 `STOCK` 流水写入，包括领用、归还、入库、调整和撤销，都在同一事务递增。版本变化用于识别“减少后又增加、数量恰好相同”的情况。
- 提交时检查盘点草稿版本和每行库存版本。任一行变化，整张不记账，返回受影响物品及期间流水；用户明确重新盘点该行后更新基准和实盘值。不能仅刷新基准、保留旧实盘值后静默提交。
- 已核对且库存版本未变化的行保留。未盘的行须补录或在草稿中明确移除后才能提交。
- 盘盈创建已有 `ADJUSTMENT` 来源；盘亏复用 `takeStock` 的现有来源分配规则，保留来源追溯与非负余额约束。
- 完成盘点、创建调整、写库存流水、审计和幂等回执必须在一个事务中完成。重复点击或网络重试只产生一次结果。
- 记账日使用提交时的业务日期，明确展示；盘点基准时间和填写时间独立保留。继续验证不能早于来源后续出入库日期。
- 已完成的盘点只读。撤销有差异的盘点时复用已有调整单撤销规则，并在同一事务更新盘点状态；从调整单入口撤销时也同步更新盘点。存在后续依赖时给出相关记录，拒绝越过依赖。
- 无差异盘点撤销只改变盘点状态并记原因，不生成流水。草稿放弃保留记录，状态为 `CANCELLED`。

状态：`DRAFT → POSTED → VOIDED`，或 `DRAFT → CANCELLED`。允许不同盘点草稿覆盖同一物品，页面提示已有进行中盘点；先提交的结果会使另一张草稿的库存版本过期。

### 2.3 验收例子

纸账面 10 盒、实盘 8 盒，笔账面 0 支、实盘 5 支：提交后分别写入 -2 盒和 +5 支，数量按物品展示。纸填写后又领用 1 盒，即使后来归还 1 盒使账面恢复为 10，也必须要求重新核对纸；本次纸和笔都不产生部分调整。

## 3. 低库存预警与补货草稿

### 3.1 补货规则设置

为需要持续备货的物品启用补货规则，设置：安全库存、目标库存、可选采购倍数、备注。默认全部关闭；历史物品不会在升级后自动被标记为缺货。

约束：`0 ≤ 安全库存 ≤ 目标库存`，目标库存大于零；采购倍数未设置时不取整，设置时必须大于零，始终使用物品现有单位。例如单位为盒、倍数为 5，就是每次建议补 5 盒的整数倍，不引入单位换算。

库存页物品卡展示当前库存、规则及缺口；设置支持逐项编辑和有确认预览的批量启停。阈值的批量覆盖须逐项展示新旧值。

### 3.2 计算口径

最重要的区别是“为部门采购、可能直接发放”和“明确准备补库存”的采购。新增申请用途 `GENERAL / STOCK_REPLENISHMENT`，历史和现有普通人工录入默认 `GENERAL`；由补货草稿生成的申请明确使用 `STOCK_REPLENISHMENT`，提交后用途只读。

按物品计算：

| 符号 | 含义 | 计入条件 |
| --- | --- | --- |
| S | 当前在库量 | 现有 `STOCK` 余额汇总 |
| P | 已确认补货申请的待采购量 | 仅补库存用途，扣除明确取消的部分 |
| T | 补货采购的待到货量 | 仅补库存用途；使用现有取消、退货、换货后的有效剩余量 |
| R | 补货的到货待处理量 | 仅补库存用途的 `RECEIVING` 余额 |
| D | 其他有效补货草稿中的计划量 | 仅 `DRAFT`；编辑当前草稿时排除自身 |

系统同时展示各部分来源，不把它们合成一个“可领用库存”。普通申请的待到货只作为参考，不能自动抵扣补货缺口。

当 `S < 安全库存` 时产生低库存提示。初始建议数量：

```text
原始缺口 = max(0, 目标库存 - S - P - T - R - D)
建议补货量 = 原始缺口（未设倍数）
建议补货量 = 向上取整到采购倍数（已设倍数）
```

数量计算全部使用定点整数。页面区分“需要新增补货”“已有草稿待确认”“已有补货待采购/到货/入库”；物理库存低的事实在补货未入库前继续显示。未低于安全库存时不自动建议，管理员仍可手动建立补货草稿。

P、T、R 是同一补货流程的互斥阶段：采购把 P 转为 T，到货把 T 转为 R，入库把 R 转为 S，不能重复相加同一批量。取消、退款、换货、直发及撤销后从现有业务事实重新计算。如果补货物品实际直发给员工，R 减少而 S 不增加，缺口应重新显现。

例：安全库存 5 盒、目标 15 盒，当前 S=2，P=3，T=4，R=1，其他草稿 D=2，则原始缺口 3 盒；采购倍数为 5 时建议补 5 盒。另有普通部门申请待到货 20 盒，不影响上述计算。

### 3.3 草稿到申请

1. 勾选建议物品，打开生成预览；逐项显示上述算式、建议量和已有草稿入口。
2. 保存为补货草稿。允许删行、改数量、补部门和经办人，保存带草稿版本号；一份草稿同一物品只有一行，最多 200 行。
3. 草稿数量可超过系统建议，界面明确展示差异和原因输入；建议不是采购事实，保存草稿不改变库存或采购数量。
4. 创建或修改草稿时校验服务端建议依据的摘要，包括当前库存、有效补货进度、其他草稿和规则。依据过期返回最新预览，保留人工填写内容，让用户重新确认；同事务计算和写入避免并发生成重复建议。
5. 确认转申请时重新计算，排除当前草稿自身。申请日期、部门、经办人及明细均须有效；有 OA 号就填写，无 OA 号复用现有系统编号。
6. 使用现有 `createRequestTx` 创建申请；草稿转为 `CONVERTED`、关联申请、写审计和幂等回执同事务提交。一份草稿只能转换一次，前往申请后仍按原流程登记供应商、价格、采购、到货和入库。
7. 草稿放弃后不再计入 D。转换后不再计入 D，而由对应申请的 P/T/R 接替。已转换且无业务记录的申请被删除时，草稿保留历史及生成时的申请编号、显示“申请已删除”，关联允许置空；不重新变成有效草稿，建议根据当前事实重新生成。

已有普通申请和在途不能由程序猜测为补库存。需要将存量补货计划纳入时，另做显式标注流程，避免迁移时错误分类。

## 4. 采购跟进台

### 4.1 两种跟进对象

| 对象 | 粒度 | 未完成条件 | 主要操作 |
| --- | --- | --- | --- |
| 到货跟进 | 采购明细行 | 有效待到货量大于零 | 修改预计到货日、记录跟进、登记到货、查看关联申请和换货记录 |
| 发票跟进 | 采购单 | 未开票，或已开票但无发票附件 | 记录跟进、修改开票状态、上传发票、查看付款信息 |

到货按采购行跟进，允许同一采购单中不同物品承诺不同日期。批量设置日期可一次覆盖所选行，提交前展示影响范围。更细的分批承诺日期作为后续扩展，当前日期表示该行剩余到货的承诺日期。

换货会进入现有待到货数量；跟进页展示换货来源和原因，但不把同一剩余数量再建一条独立换货待办。存在普通未到货与换货同时待补时，界面说明合计口径，避免伪造具体批次的履约情况。

发票跟进与付款状态独立。登记“无需跟进”并填写原因可以隐藏待办，不把它伪装为已经开票或已上传附件。

### 4.2 页面与日期

- 顶部显示今日需跟进、已逾期、未设计划的数量；列表支持类型、供应商、日期、申请号、物品及状态筛选。
- 每行展示采购编号、关联申请、供应商、剩余数量及单位、预计完成日、下次跟进日、最近记录。
- 预计到货日早于今天且仍未到齐才标记“到货逾期”；没有预计日只展示已等待天数及“未设到货日”。发票可另设预计取得日期，同样明确区分逾期与未设日期。
- 下次跟进日为今天或过去、且事项仍未完成时，进入“今日需跟进”。支持改期；逾期标签仍按业务承诺日期计算，不被跟进改期掩盖。
- 日期按服务器配置的业务时区统一判断，日期字段使用 `YYYY-MM-DD`。页面重新获得焦点、跨日和可见期间的定时刷新都会更新待办，后台隐藏页面停止轮询。
- 跟进记录包含时间、备注、调整后的日期和变更前值；已有记录保留，补充说明用追加记录。

### 4.3 自动完成与恢复

- 到齐或取消剩余量后，到货事项自动转为完成；开票且上传发票后，发票事项自动转为完成。
- 撤销到货、再次换货、撤销开票或删除最后一份发票后，重新依据业务事实出现；显示重新出现的原因和旧计划，允许重新安排日期。
- 采购被撤销后从活跃跟进中移除，历史计划和记录仍可查看。
- “已完成”由事实计算；“已忽略”是管理员明确设置并填写原因的管理状态。业务恢复不会自动消除明确忽略，已忽略页可恢复跟进。
- 工作台查询实时派生当前待办，计划和日志只存人工设置与历史；不用一张可被忘记更新的待办余额表替代业务状态。
- 记录跟进只改变计划和备注，不直接代替到货、开票或付款登记。业务按钮继续使用现有操作弹窗。

## 5. 数据结构与接口

### 5.1 数据模型

| 模型 | 主要新增字段或用途 |
| --- | --- |
| `CatalogProduct` | `stockVersion`，默认 0；STOCK 流水与版本递增同事务 |
| `Stocktake` | 标题、说明、状态、草稿版本、创建/提交/撤销时间、撤销原因、唯一可空 `adjustmentDocumentId` |
| `StocktakeLine` | 盘点 ID、物品 ID、品名/规格/单位快照、基准库存/版本/时间、实盘数（可空）、填写时间、差异原因；盘点与物品组合唯一 |
| `StockPolicy` | 物品唯一、启用、安全库存、目标库存、可空采购倍数、备注、版本 |
| `ReplenishmentDraft` | 标题、部门、经办人、日期、状态、版本、生成申请关系、生成时申请编号快照、创建/确认时间 |
| `ReplenishmentDraftLine` | 草稿 ID、物品及名称/规格/单位快照、拟补数量、保存时建议依据、超出建议原因；草稿与物品组合唯一 |
| `ProcurementRequest` | `purpose`，默认 `GENERAL`；新补货申请为 `STOCK_REPLENISHMENT` |
| `PurchaseFollowup` | 类型、采购行或采购单关系、预计完成日、下次跟进日、忽略时间/原因、版本；目标唯一 |
| `PurchaseFollowupEntry` | 跟进计划关系、时间、备注、变更前后值；追加保存 |

补货规则与新草稿默认不创建历史记录。迁移通过 CHECK / 外键 / 唯一约束限制合法状态、非负实盘值、正补货数量和跟进目标类型；Prisma 未表达的约束在迁移 SQL 中明确维护。所有旧记录、来源关系和现有 CHECK 约束必须保留。

跟进目标二选一：`ARRIVAL` 关联采购行，`INVOICE` 关联采购单；数据库校验互斥及唯一性，服务端继续校验目标确为有效采购。

### 5.2 实际接口分组（统一 `/api/planning` 前缀）

| 接口 | 用途 |
| --- | --- |
| `GET /summary` | 盘点草稿、需要新增补货、到期或逾期跟进计数 |
| `GET/POST /counts`、`GET/PATCH /counts/:id` | 盘点列表、创建和带版本保存 |
| `POST /counts/:id/recount`、`/post`、`/cancel`、`/void` | 重盘、整单记账、取消或撤销 |
| `GET /counts/:id/export` | 盘点结果 CSV |
| `GET /replenishment/suggestions` | 物品规则与 S/P/T/R/D、来源、摘要；`excludeDraftId` 排除当前草稿，页面每页展示20项 |
| `PATCH /replenishment/policies` | 单项或批量规则设置；携带每项旧版本 |
| `GET/POST /replenishment/drafts`、`GET/PATCH /replenishment/drafts/:id` | 草稿列表、创建、版本保护保存 |
| `POST /replenishment/drafts/:id/confirm`、`/discard` | 转申请或放弃 |
| `GET /followups` | 分页跟进与汇总计数；类型、状态、供应商、预计日期、申请、搜索筛选 |
| `PATCH /followups/plans` | 单项或批量日期及追加记录；任一对象冲突整批回滚 |
| `PATCH /followups/dismiss` | 用 `dismissed` 明确停止或恢复，必须填原因 |
| `GET /followups/history?kind=…&targetId=…` | 追加记录的历史 |

写接口沿用认证、`Idempotency-Key`、审计与事务约定；保存携带预期版本。共享契约集中在 `packages/shared/src/planning.ts`。读取与写入逻辑分别集中在三个领域服务中，不拆出仅作转发的 query service。补货先按物品和申请聚合，避免逐物品扫描全部采购；列表服务端分页，补货规则和建议一次读取后在页面分页。

盘点冲突返回物品和最近200条期间流水；补货冲突返回具体物品及最新建议。页面保留输入，通过明确重盘或刷新依据重新核对。日期与跟进日志在一个批量接口中提交，替代原方案的多条单项 API，保持相同事务语义。

## 6. 实现位置与复用方式

- `apps/server/src/workflow/workflow.service.ts`：在 `stockChange` 内递增库存版本；抽出事务内的单行库存调整 helper，原手工调整和盘点批量记账共同调用。盘点提交、撤销、补货转申请继续经过现有 `write`，避免嵌套事务或多次独立提交。
- 新增 `stocktake.service.ts`、`replenishment-query.service.ts`、`replenishment.service.ts`、`followup-query.service.ts`、`followup.service.ts` 处理各自的草稿、查询和计划；控制器仅做输入校验与路由。需要复用的事务/幂等包装集中提取，保持现有命令语义。
- 现有 `WorkflowQueryService` 的待采购、待到货和待处理数量提取为内部可复用的投影函数；补货和跟进使用同一口径。列表用聚合查询及批量关联读取，不逐物品反复加载整张申请。
- 新增盘点、补货、草稿编辑及跟进视图；扩展现有 `StockView` 页签与 `WorkView` 待办。只提取必要的共享申请头/明细编辑组件，确认转申请直接复用现有创建逻辑。
- 继续使用现有 UI 组件、定点计算、CSV 保护、URL 筛选、草稿版本和 API 幂等机制。无需新增运行时依赖。
- 审计增加盘点创建/保存/提交/撤销、规则变化、草稿转换、跟进改期/忽略/恢复等动作，展示中文和新旧值，记录所关联的业务对象。

## 7. 分阶段实施与出口

| 阶段 | 实施步骤 | 可演示结果与出口 |
| --- | --- | --- |
| M0：基础口径 | 固定上述状态、日期、用途、公式与并发规则；核对上一轮改动与现有测试基线；加入接口样例及迁移设计 | 规则与示例可直接用于后续测试，保留上一轮完整工作区 |

## 8. 必测场景

1. 盘点空白与零不同；小数精度边界；盘盈盘亏混合；无差异不产生空流水。
2. 填写后发生入库、领用、归还、退货、调整或撤销；数量恢复原值仍判版本冲突；任一行冲突整单不记账。
3. 草稿跨浏览器编辑冲突；保存失败保留输入；重复提交、同时重试只产生一份调整或申请。
4. 盘亏跨多个库存来源分配正确；撤销受后续依赖限制；盘点入口与调整单入口撤销联动一致。
5. 补货只统计同一 productId；不同规格和单位分开；普通部门采购的在途不抵扣缺口。
6. S/P/T/R/D 阶段迁移守恒；部分采购、部分到货、入库、直发、退款、换货、取消与撤销后建议正确。
7. 多个草稿相互可见、排除当前草稿自身；放弃释放计划量；转换后 D 消失且 P/T/R 接替；生成申请被合法删除后不继续虚增计划量。
8. 采购倍数用定点整数向上取整；规则调整或业务数量变化后旧预览不能无提示写入。
9. 日期以业务时区判断；当日到期、昨天逾期、跨日、未设置日期、改期但仍业务逾期分别正确。
10. 采购跨多张申请、部分到货、换货后重新出现；发票状态与附件独立；删除最后一份附件后重新待跟进；采购撤销后保留历史。
11. 所有新接口需要登录，非法用途、非采购目标、重复产品、错误版本、负数量和不合法状态迁移被拒绝。
12. 390px 手机完成盘点与补货，批量确认能读清影响；CSV 与页面筛选口径一致；深浅主题与读屏标签可用。
13. 在隔离数据库迁移现有结构，验证旧申请、采购、附件、库存及幂等记录完整；有新草稿、新跟进和已完成盘点的备份恢复后版本、关联和旧会话处理正确。
14. 使用 200 行盘点、千级物品及万级业务流水夹具，检查查询分页和事务实际耗时；200 行记账须在现有 30 秒事务上限内完成，并保留所有失败时的原子性。

验证命令沿用仓库：shared 构建、`pnpm typecheck`、`pnpm lint`、`pnpm test`、server/web 构建、真实浏览器功能测试、固定 Playwright 容器视觉回归；迁移及备份恢复在临时库或隔离容器完成。

## 9. 交付和后续扩展

交付包含业务页面、API、数据库迁移、回归测试、视觉基线、CHANGELOG、升级与验收记录。生产数据与配置不属于本次方案编写或本地实现的修改对象。

新增表是增量变化，但启用 `stockVersion` 后，旧应用不会维护该版本。回退必须停写并配套恢复升级前备份，或者在重新升级后作废所有未完成盘点的基准、要求重盘；不能仅因数据库列仍兼容就认定旧应用可与新盘点流程混跑。发布演练采用前者，并记录回退会丢弃备份之后的业务变动。

本轮完成后的两个扩展：

- 历史采购价对比：按相同物品、规格、单位比较供应商实际成交价，连到原采购与链接；为补货草稿选择供应商提供参考。
- 常用采购模板：保存常用物品组合及默认数量，复用本轮的补货草稿编辑与确认机制；每次生成独立草稿，由管理员确认本次数量。
