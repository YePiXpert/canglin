# Beta 2：采购执行、金额对账与手机作业

更新日期：2026-10-23。源码版本 `1.0.0-beta.2`，当前为本地开发交付，尚未提交、推送、打标签或部署。生产仍为 `v1.0.0-beta.1`。

本轮按用户确认完成 **1、3、5、6、7**。询价比价、采购模板和周期采购不在范围内。

## 使用入口

工作台、申请单和库存页增加「采购执行」导航；手机也可从底部「更多」进入。

| 入口 | 可以完成的操作 |
| --- | --- |
| 集中采购 `/procurement` | 跨申请筛选待采购需求、跨页选取、建立或追加批次；同一需求拆供应商，填写实际数量、成交价和链接；按供应商一次生成采购单，保留每行来源；导出与打印 |
| 资金对账 `/finance` | 分次付款、同供应商合并付款、退款、员工垫付、报销及员工退回；逐采购分配金额、上传凭证、撤销错录；历史期初核实与重核 |
| 发票池 `/finance/invoices` | 票面与原件、历史附件关联、PDF 文本或 AI 图像预填；一票多单、多票一单、冲减原票、作废纠错；金额匹配后影响采购状态 |
| 手机作业 `/operations/mobile` | 相机连续扫码、二维码照片、手输或物品查找；到货、入库、直发、库存领用清单；按领用人拆行、建立盘点、保存到服务器核对 |
| 标签 `/operations/labels` | 生成物品或业务单据二维码并打印；二维码含本站地址与编号，打开后仍须登录 |
| 操作草稿 `/operations/drafts` | 找回、编辑、查看当前来源与额度、重新核对、执行或放弃；AI 原建议与人工修改分别保留 |
| 异常中心 `/workbench/exceptions` | 到货逾期、到货待处理、补货缺口、历史资金待核实、待退款、员工应退、票据差异、超期草稿；暂缓、忽略、恢复和历史 |
| 月度复盘 `/insights/monthly` | 月度采购和资金、供应商交付时长、部门/个人净领用，以及当前逾期和长期未领用库存；来源跳转、CSV 与打印 |

### 一次完整业务

1. 在需求池选择多份申请的剩余行，建立采购批次。按实际下单情况拆行，填供应商、数量、单价，先保存再确认下单。任一来源数量不足时整批失败。
2. 打印采购单标签；手机扫码，填本次实收数量，保存草稿并确认到货。继续扫描到货单入库；需要直发时先选「到货直发」再扫码。库存领用扫物品标签。
3. 在执行结果上传到货照片或签收凭证。盘点复用现有盘点流程；入库草稿不另造到货凭证。
4. 资金对账记录实际付款。员工垫付先记为供应商付款，再从该原付款登记报销；收到退款和员工退回款分别登记。
5. 录入发票并核对原件，分配到同供应商采购单，确认后计入有效票据金额。采购取消/退货后出现票据超额时，登记关联原票的冲减票据。
6. 在异常中心处理后续事项，月末按实际发生月份复盘。

## 数量、资金与票据口径

- 数量六位、单价四位、金额两位小数；仍用整数定点运算，逐行金额四舍五入后汇总。
- 净采购 = 成交原额 − 取消采购 − 退款退货冲减。登记退货不会伪造已经收到现金退款；换货不冲减成交额。
- 净实付 = 有效付款及核实期初 − 实际退款。待付款和待退款分别取净采购与净实付差额的正数。
- 允许登记真实超付，超出部分进入待退款，不能为使对账好看而截掉实际金额。
- 报销是公司与员工的往来，不增加供应商实付。按每笔原垫付及其采购分配计算待报销/应退回，甲的待报销不抵销乙的应退回，合并付款的不同采购也不相抵。
- 每笔分配合计须等于实际总金额；退款、报销和员工退回须关联有效原付款，逐采购校验额度及日期。撤销有依赖的记录须先处理下游。
- 有效票据金额 = 已确认普通发票匹配 − 已确认冲减票据匹配。草稿或作废票据不计入。匹配不能超过净采购，冲减不能超过原票及其采购分配。
- 发票原件、票面和金额分配是不同步骤。可先确认未完全匹配的票据，余款会出现在异常中心。供应商与有效票号不能重复；作废错误记录后允许同号重新登记。
- 上传相同文件到另一张有效发票会提示重复。一个 PDF 包含多张票时须先拆成每票一份原件。历史采购附件可关联到发票，保留原附件引用。

### 历史数据

迁移后的旧采购保持 `LEGACY`，旧「已付款/已报销」标记不推算为金额或日期。界面新采购和集中采购使用 `DETAIL`；旧 API 未提供 `settlementMode` 时继续按历史语义创建。

核实期初时填写截至日期、付款主体、净实付及员工已报销余额，也可明确确认为没有付款。历史供应商退款后，员工已报销可超过净垫付；即使净垫付为0，也能保留员工应退余额，不补造当月付款或退款。期初不算当月现金收支。没有有效后续资金往来时，可重新核对期初；旧记录保留撤销原因，不覆盖历史。

采购详情、旧付款清单与跟进台共用新的金额投影。金额对账采购不再直接编辑付款/开票布尔标记；已匹配票据的历史采购也不能用旧开票标记覆盖事实。

### 月报

采购按各业务事件日期；现金按实际记录日期，跨月撤销在撤销月份冲回。供应商交付时长是本月有效收货明细批次的平均天数。当前到货逾期、历史待核实数量和长期未领用库存是当前快照，不冒充选定月份的历史余额。供应商付款与员工报销不能相加为采购成本。

## 草稿、冲突与失败恢复

批次、票据、资金分配及操作草稿校验预期版本，使用同事务审计和幂等回执。相同提交重试不会重复下单或发放；整批发生冲突不留下部分单据。

手机清单在当前设备的当前标签页暂存，刷新可继续；退出登录会清除。保存到服务器后可跨设备继续。网络失败保留数量；来源变化后旧草稿不能执行，须明确重新核对，可保留未保存输入。扫码不直接记账，重复识别同一标签不累加数量。暂存不等于离线记账，最终保存和执行需要网络。

资金表单遇到版本冲突时保留输入，「核对最新余额」更新依据，用户核对后再提交。发票原件上传失败时保留已建草稿编号，重试只补原件。已确认/作废发票原件与资金凭证保留；待核对发票可移除错误原件。

异常的暂缓/忽略只处理提醒，不改变业务。暂缓到期重新提醒，实际条件解除后从待处理移除；人工处理历史保留。页面可见、重新获得焦点以及跨日后重新计算。

## AI 与数据发送

AI 可整理所选采购需求、提出发票金额匹配，或查询新对账/异常/月报。写入始终由人工在草稿详情确认：采购建议执行后只建立采购批次草稿，尚需填写并确认实际下单；发票建议执行只修改匹配，不自动确认票面。

生成前后校验业务依据，范围外 ID、超额金额、非法结构和生成期间的变更会拒绝。保留整理要求、原建议、解释与人工编辑结果。执行前再次校验；模型没有业务写工具。

- 操作草稿会把整理要求和所选需求、采购、票面及对账金额发送到已配置的模型服务。
- 发票本地模式提取 PDF 文本层；图片或没有文本层的 PDF 可人工填，或主动选择 AI。AI 将选定的一页原件图发送到配置的服务，不自动把整份文件逐页发送。未知字段留空。
- 二维码相机和照片在浏览器本地解码。到货/签收照片只有点击上传才存入本机服务附件目录，不自动发送给模型。
- 模型调用失败可重试；成功重试复用草稿。并发同请求不重复调用。服务重启导致结果未知时，首次重试提示本次没有调用服务；用户再次点击才重新请求。
- 本轮模型与 OCR 调用使用模拟响应测试，未验证具体服务商的真实发票识别准确率；所有识别结果仍需人工核对。

## 数据库与接口

新增迁移 `20261024000000_execution_settlement`：采购批次及行、资金记录及分配、发票及分配、异常处理及历史、执行草稿。旧业务表只追加列，保留数量账的外键和 CHECK。附件增加新归属及内容哈希，通过触发器限制只能属于一个业务对象。有效供应商票号使用部分唯一索引，不能用 `db push` 代替发布迁移。

接口统一在 `/api/execution`：

| 分组 | 主要接口 |
| --- | --- |
| 集中采购 | `GET demands`；`GET/POST batches`；`GET/PATCH batches/:id`；`POST batches/:id/confirm`、`cancel`；`GET batches/:id/export` |
| 资金 | `GET settlements`；`POST settlements/:id/opening`；`GET/POST financial-records`；`GET financial-records/:id`；`POST financial-records/:id/void` |
| 发票 | `POST invoice-recognition`（multipart，`mode`/`page`）；`GET/POST invoices`；`GET/PATCH invoices/:id`；`PATCH invoices/:id/allocations`；`POST invoices/:id/post`、`void` |
| 异常/月报 | `GET exceptions`、`exceptions/history`、`exceptions/rules`；`PATCH exceptions/rules`；`POST exceptions/action`；`GET monthly-review?month=YYYY-MM` |
| 操作草稿 | `GET/POST drafts`；`GET/PATCH drafts/:id`；`GET drafts/:id/context`；`POST drafts/:id/recheck`、`execute`、`discard`；`POST ai-proposals` |

附件继续使用 `/api/attachments`，新增 `financial-records/:id`、`invoices/:id` 上传以及 `invoices/:id/link` 关联历史原件。业务写接口需要登录与 `Idempotency-Key`；附件采用自身重复文件校验及审计。文件下载保持登录鉴权。

## 升级与回退

1. 发布前保留完整库、附件、密钥、配置及旧镜像摘要；停止业务写入。
2. 使用发布提交对应镜像执行真实增量迁移，再检查 `/api/health`、历史记录和新入口。旧应用不能继续写入同一数据库。
3. Beta 1 生产目录的 Compose override 固定了三个镜像摘要，仅修改 `RELEASE_TAG` 不会换镜像；发布时核对最终 Compose 配置和三个运行摘要。
4. 回退必须成对恢复升级前数据与旧镜像，不能让旧应用写入包含新资金/票据的库。回退会丢弃备份后的业务变动。
5. 本次没有更新生产服务、创建发布标签或运行推送。
